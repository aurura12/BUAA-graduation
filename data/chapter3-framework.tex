\chapter{系统架构与技术路线}

\section{总体研究方案}

本文采用数据驱动感知、大模型状态图调度、多工具并行执行的总体方案。首先，利用PeMS08交通传感器网络的大规模时空序列数据，对数据进行清洗和标准化处理，得到结构化的交通态势特征库，给后面的Agent推理提供高保真的感知输入 \upcite{ref47_zou2024atstgcn, ref53_wang2025congestion}。接着用本地部署的Qwen3.5-9B大语言模型做智能体的推理引擎，配合精心设计的系统提示词来完成复杂的交通任务指令意图拆解 \upcite{ref44_qin2025llmsurvey}。本文根据交通任务强时效、多并发的特点，用LangGraph框架来创建状态图(StateGraph)循环执行引擎 \upcite{ref45_xi2026llmagent}。Agent在一次推理中可以产生许多不同的工具调用指令，这些指令会被工具执行节点并行地分发到底层服务上。最后将大模型的语义理解能力同PDFormer时空预测模型深度整合，创建起一个包含流量查询、历史追溯、时空演变预估的闭环原型系统，给城市交通管理决策赋予智能化支撑 \upcite{ref31_jiang2023pdformer, ref43_yin2026dgctransformer}。


\section{技术路线}

本文技术路线由下到上分为五层，分别为感知层、认知层、决策层、执行层和应用层。感知层主要解决多源异构交通数据清洗、对齐、特征组装的问题，认知层用本地化部署的大模型做自然语言指令的语义解析和子任务拆解，决策层用状态机(State Machine)的思想来编排智能体的思考和工具调度逻辑，用双重兼容的解析机制保证并行工具调用的可靠性，执行层负责具体的领域模型调用，包含历史趋势的深度分析以及基于时空图卷积的流量预测，应用层注重工程落地，用FastAPI和SQLite创建具有高并发响应和时序记忆能力的后端微服务 \upcite{ref42_lijian2025transkg}。经过这样的分层架构设计之后，系统就达成了逻辑控制权和计算执行权相分离的效果，从而保证了在复杂的交通长尾情形之下依然可以保持鲁棒性以及扩展性。

\subsection{感知层}

感知层属于系统底层的数据根基，它要解决诸多来源、种类繁杂的交通数据的清洗、融合、时空校准等难题。在实际的交通场景当中，传感器数据出自各种各样的采集设备以及通信协议之中，因此就会存在时间戳不同步、字段空缺、格式各异等情形 \upcite{ref51_yi2024vicsurvey}。本文首先对原始流数据进行统一的标准化处理、缺失值插补，然后根据路网拓扑结构把碎片化的点位流量映射到全局图结构特征矩阵上 \upcite{ref52_yao2025taidgcn}。用某种数据滑动窗口来把连续时间序列切分成符合下游模型输入要求的离散时间步特征矩阵。该过程可以消除由于多源数据不一致、传感器缺失造成的噪声干扰，给之后的预测引擎和智能体分析提供标准、高质量的时空感知输入。

\subsection{认知层}

认知层起着系统“大脑”的作用，用预训练的大语言模型来解析交通管理意图。系统选用 Qwen3.5-9B作为核心推理引擎,并设计了结构化的系统级提示词（System Prompt） \upcite{ref44_qin2025llmsurvey}。提示词中明确给出了三个可以使用的工具接口规范以及选择标准，即仅查询时使用 simple\_query，需要分析研判时使用 deep\_analysis，需要预测时使用 predict\_traffic。提示词同时约束了数据截取与展示规范，例如预测结果默认返回未来 1 小时共 12 个时间步，若用户指定更短时间范围则由 Agent 自行在报告中截断。当用户指令进入认知层后，模型能够自动识别长文本指令中的实体 ID 与时间参数，将宏观交通任务拆解为细粒度的子任务序列，从而为决策阶段的并发工具调度奠定认知基础 \upcite{ref45_xi2026llmagent}。在工具调用格式上，系统采用 XML 标签协议：Agent 可在单次回复中输出多个独立的 \texttt{<tool\_call>} 标签块，每个标签内使用 \texttt{<function=...>} 子标签指定工具名，使用 \texttt{<parameter=...>} 子标签传递参数。

\subsection{决策层}

决策层就是认知意图和底层执行之间的桥梁。本层级引入 LangGraph 框架构建基于有向循环图(StateGraph)的状态流转机制 \upcite{ref45_xi2026llmagent}。系统定义了两个核心图节点:大模型推理节点(Agent Node)与工具执行节点(Tool Execution Node)。Agent Node负责调用LLM生成工具调用指令,Tool Execution Node基于 LangGraph预置的 ToolNode实现,负责接收工具调用列表并实际执行。两节点之间用条件路由边连接，条件边会检查AgentNode输出消息的tool\_calls属性是否不为空。如果包含有效的工具调用,则流转至 ToolExecution Node,执行完成后回到 Agent Node继续推理。如果为空，即模型已经完成了分析，满足结束条件END，结束当次推理循环。

针对大模型在生成工具调用时可能出现的格式偏差问题，Agent Node 内部集成了双重兼容的解析机制。优先使用 LangChain 的 \texttt{bind\_tools} 通道，让大模型直接生成符合 OpenAI 函数调用规范的结构化工具调用数据。如果原生通道未产生工具调用，而模型输出的文本中又包含 \texttt{<tool\_call>} 标签，节点会自动切换到正则回退模式：首先用非贪婪正则表达式 \texttt{<tool\_call>(.*?)</tool\_call>} 提取每个标签块的内容，然后在块内匹配 \texttt{<function=...>} 和 \texttt{<parameter=...>} 子标签以提取工具名和参数值，最后构造等价的工具调用对象并替换原响应消息。双重机制可以实现标准API通道可靠和原生XML格式兼容的目的，不会因为一次格式不一致而使整个推理过程中断。
\subsection{执行层}

执行层是系统闭环能力的落脚点，由三个专业化的领域工具构成。每个工具均以统一的函数签名（\texttt{entity\_id} 与 \texttt{time}）对外暴露，便于 Agent 进行标准化调用：

\textbf{（1）态势查询工具（simple\_query）。}通过调用后端 RESTful 接口获取指定传感器在特定时刻的流量、速度与占有率等瞬时交通状态，适用于点位级的实时快照查询。

\textbf{（2）深度分析工具（deep\_analysis）。}在获取当前时刻数据的基础上，额外拉取该传感器过去 3 小时的连续历史趋势序列，为 Agent 提供具备时间纵深的多维分析素材，适用于交通态势的成因追溯与趋势研判。

\textbf{（3）时空预测工具（predict\_traffic）。}该工具在执行时会自动完成全局路网特征矩阵的组装：首先遍历全路网所有传感器节点，从后端记忆库中分别拉取各自过去 1 小时（共 12 个时间步）的历史流量序列；随后按时间戳对齐并聚合为完整的时空特征矩阵；最后将矩阵序列化后发送至后端的时空预测引擎（如 PDFormer 架构）进行推理 \upcite{ref31_jiang2023pdformer, ref47_zou2024atstgcn}。预测引擎返回未来 1 小时（每 5 分钟一个预测步，共 12 步）的全路网流量预测结果，工具从中提取目标节点的预测序列并以结构化 JSON 报文返回给 Agent。通过将深度学习模型的黑盒预测结果转化为可解析的定量决策依据，执行层完成了从原始感知数据到智能分析结论的实质性转化。

\subsection{应用层}

应用层聚焦于原型系统的工程落地与交互闭环。系统后端基于 FastAPI 框架开发，以微服务架构承载高并发的请求解析与 Agent 调度，并利用 SQLite 构建轻量级、具备时序查询能力的本地记忆库 \upcite{ref42_lijian2025transkg}。通过封装友好的 RESTful 接口，应用层不仅负责综合呈现包含实时态势监控与未来演化预测的最终分析报告，还支持在真实多维度的交通运维场景中开展交互测试，充分验证该协同架构在长尾并发任务下的泛化性能与实用价值。


\section{技术开发环境与实现工具}

\begin{itemize}
    \item \textbf{开发语言}：Python 3.10
    \item \textbf{后端服务框架}：FastAPI
    \item \textbf{大语言模型底座}：Qwen3.5-9B
    \item \textbf{Agent 调度与控制框架}：LangChain / LangGraph (状态图范式)
    \item \textbf{时空交通预测模型}：PDFormer（基于图卷积的时空预测架构，实验验证采用 PEMS08 数据集）
    \item \textbf{数据库管理}：SQLite
\end{itemize}
