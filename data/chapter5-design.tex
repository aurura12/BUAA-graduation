\chapter{基于大模型的交通智能体设计}
\section{交通智能体总体架构设计}

本研究设计的交通智能体采用“慢思考”与“快反应”相结合的双层驱动架构。该架构基于 LangGraph 构建，核心是一个具备记忆能力的 ReAct（Reasoning + Acting）推理循环。

慢思考层由 Qwen3.5-9B 大语言模型驱动。智能体在收到用户指令后，大模型负责理解用户意图，确定需要调用哪些工具，并生成结构化的工具调用指令。这个过程体现了智能体对交通语义的深度推理。

快反应层由工具执行引擎负责。该引擎解析大模型输出的工具调用指令，并行调用底层的数据查询、深度分析或流量预测服务，然后将结果以统一格式返回给大模型。

与传统的线性管线相比，这种双层循环架构有三个关键优势。第一，大模型可以在单次推理中决定并行调用多个工具，从而显著减少系统的响应时间。第二，系统通过提示词模板来约束大模型的行为，防止模型在复杂交通语境下产生幻觉。第三，工具执行与语义推理在工程层面完全解耦，工具链可以独立扩展，不会影响核心推理逻辑。

智能体的工作流程分为三步。第一步，用户发出一个自然语言指令。第二步，推理节点（Agent Node）分析该指令，根据系统提示词中预定义的三个工具来决定需要调用哪些工具，然后生成结构化的工具调用对象。如果大模型原生输出的文本中含有 XML 格式的工具调用标签，推理节点会自动将其解析为标准工具调用对象。第三步，工具执行节点（Tool Execution Node）接收这些工具调用，并行执行对应的工具函数。执行结果返回给推理节点后，大模型综合这些结果，生成条理清晰的分析报告返回给用户。如果推理节点判断不需要调用工具，循环会直接结束并输出最终回答。

\section{语言大模型选择与部署方案}

为了保证交通智能体的推理质量，本研究选用 Qwen3.5-9B 作为核心决策引擎。该模型属于 Qwen3 系列，基于 Transformer 架构，在预训练阶段吸收了大规模语料。Qwen3.5-9B 拥有更大的参数规模和更强的指令遵循能力，在复杂交通语境下的意图理解与多工具协同调度方面表现更优。本研究使用的 Qwen3.5-9B 为原始精度版本，未进行量化压缩，以保留模型的完整推理能力。

在部署方式上，本研究将 Qwen3.5-9B 模型部署在本地 GPU 服务器上，通过 vLLM 推理框架对外提供 OpenAI 兼容的 API 服务。vLLM 是一个高性能的大模型推理引擎，它使用 PagedAttention 机制来高效管理 GPU 显存中的键值缓存，从而在保证推理速度的同时支持更大的上下文窗口。以下为具体的部署命令：

\begin{lstlisting}[
    language=bash,
    caption={使用 vLLM 在本地服务器部署 Qwen3.5-9B},
    label={code-vllm-deploy},
    breaklines=true,
    frame=single,
    numbers=left,
]
python -m vllm.entrypoints.openai.api_server \
    --model MODEL_PATH \
    --served-model-name qwen-7b \
    --host 0.0.0.0 \
    --port 8002 \
    --tensor-parallel-size 1 \
    --gpu-memory-utilization 0.45 \
    --max-model-len 20480 \
    --trust-remote-code \
    --api-key "sk-local-api-key"
\end{lstlisting}

部署完成后，智能体通过 HTTP 请求向本地 vLLM 服务端点发送对话消息，调用方式与 OpenAI 官方 API 完全一致。因为模型运行在本地服务器上，数据传输不需要经过外部网络，这既保护了交通数据的隐私性，也避免了云服务可能带来的网络延迟波动。API 的 temperature 参数设置为 1.0，top\_p 设置为 0.95，为模型在生成分析报告时保留了较高的表达灵活性。

在上下文长度方面，vLLM 部署时将最大序列长度设置为 20480 个 Token。这个窗口大小足够让智能体同时感知多个传感器节点在过去较长一段时间内的历史特征数据，并在不截断上下文的前提下进行长时程的语义分析与推理。20K 的上下文窗口为复杂的多工具协同调用和深度交通分析提供了更大的信息容纳空间。

\section{基于状态图的推理逻辑与节点设计}

智能体的核心推理过程被封装在两个相互协作的逻辑节点中，它们通过 LangGraph 的有向状态图进行编排。

\textbf{推理节点（Agent Node）}是智能体的核心决策模块。它内部包含一个经过精心设计的系统提示词，该提示词明确定义了智能体可以使用的三个核心工具及其参数规范。当用户指令进入推理节点后，大模型会执行以下步骤：首先理解用户意图，然后确定需要调用哪些工具，最后输出结构化的工具调用指令。

在工具调用的解析上，推理节点采用双重兼容机制。系统优先使用 LangChain 原生的 \texttt{bind\_tools} 通道，让大模型直接生成符合函数调用规范的结构化数据。如果原生解析未产生工具调用，而模型输出的文本中又包含 \texttt{<tool\_call>} 标签，节点会自动切换到正则回退模式，用正则表达式匹配 \texttt{<function=...>} 和 \texttt{<parameter=...>} 子标签，从中提取工具名和参数值，再构造出等价的工具调用对象。这种双重机制兼顾了标准 API 通道的可靠性和原生 XML 格式的兼容性。

系统提示词的设计遵循三个约束原则。第一是工具空间约束，模型的工具选择被严格限定在 simple\_query、deep\_analysis 和 predict\_traffic 三个工具之内，防止模型生成无效的工具调用。第二是并行调用规范，提示词鼓励模型在需要时一次性输出多个独立的工具调用标签，以并行方式完成多个子任务。第三是数据展示规范，对于预测任务，模型会根据用户指定的时间范围自行截断数据，避免输出冗余信息。

代码~\ref{code-tool-call}~展示了工具调用的 XML 格式。

\begin{lstlisting}[

\textbf{工具执行节点（Tool Execution Node）}基于 LangGraph 预置的 ToolNode 实现，负责接收推理节点传来的工具调用列表并实际执行。该节点的处理流程分为三步。

第一步是去重与校验。节点维护一个已执行调用的集合，防止大模型在同一轮回复中生成完全相同的工具调用请求。对于每个调用，节点会校验其工具名称是否存在于可用的工具映射表中。

第二步是并行执行。所有合法的工具调用会被并行发送到对应的工具函数中执行。三个工具各自封装了对底层 FastAPI 数据服务的 HTTP 请求，并行执行可以显著减少多工具协同调用时的响应时间。

第三步是结果汇总。各工具的执行结果以统一的消息格式返回给推理节点，供大模型进行下一步的综合分析。如果某个调用在执行过程中出现异常，节点会生成对应的错误信息，确保系统不会因为单个工具故障而中断整个推理流程。

\textbf{条件路由机制}的设计简洁而高效。LangGraph 的状态图中只包含一条条件边：检查推理节点输出消息的 \texttt{tool\_calls} 属性是否非空。如果包含有效的工具调用，则路由到工具执行节点，执行完成后返回推理节点继续推理。如果为空，说明大模型已经完成分析，直接结束流程并将最终报告输出给用户。

这种“推理-执行-再推理”的循环模式，相比传统的线性管线具备更强的异常处理能力和任务适应性。在一次用户请求中，智能体可以根据实际需要进行多轮工具调用，逐步深化对交通数据的分析。

\section{执行层工具链设计与实现}

在本项目设计的执行层中，各核心工具被封装为基于 FastAPI 异步框架的微服务节点，实现了交通智能体与物理世界数据之间的动态感知与交互。该层级通过 Uvicorn 高性能服务器进行部署，将存储于 SQLite 数据库中的 PeMS08 交通数据转化为可实时调用的计算资源。

在基础流量感知维度上，系统实现了流量感知工具的交互接口。该工具通过 \texttt{/flow/point} 端点接收来自智能体的实体标识与 ISO-8601 格式的时间参数，并在后端利用 SQL 语句的模式匹配机制对 dyna 动态表进行毫秒级的检索。为了确保数据提取的精确性与工程鲁棒性，该服务在底层数据库连接中采用了 sqlite3.Row 工厂模式，这使得原始的交通流量、道路占有率及平均速度数值能够以高度结构化的键值对形式反馈至智能体状态图中。这种设计解决了时空数据在跨模块传递过程中的格式对齐问题，为智能体提供了瞬时态势感知的物理基础。

针对更高层级的决策需求，本研究进一步设计了深度分析工具作为数据支撑。该工具的核心逻辑在于其对历史交通流量序列的动态回溯能力，通过 \texttt{/flow/history} 接口实现。服务端利用 Python 的 datetime 类与 timedelta 偏移逻辑，根据智能体下发的查询跨度参数自动计算时空起止坐标，并从数据库中提取具有连续性的流量序列。为了提升智能体在处理长序列数据时的效率，该工具在返回结果前执行初步的特征聚合，仅保留流量波动的关键时间节点，从而支撑智能体利用链式思考机制对当前路段的拥堵风险生成具有专家水准的评估报告。

在预测任务的执行过程中，预测计算工具作为智能体与底层 PDFormer 时空模型的集成中枢发挥了关键作用。该工具不再局限于单点的数值检索，而是通过在全网 170 个传感器节点上同步采集过去 12 个历史步长的全局特征，构建出完备的时序特征向量。这种基于 FastAPI 的微服务化设计实现了感知逻辑与数值计算在工程层面的完全解耦。智能体仅需通过标准的 HTTP 协议发送 JSON 格式的数据包，即可触发位于特定端口的预测引擎运行复杂的时空变换算法。预测结果最终以对齐格式的表格形式输出，实现了数值、语义与图表的多维度信息反馈。系统还集成了基于文件处理器的日志审计模块，对每一次 API 调用进行实时记录，为系统在复杂交通场景下的稳健运行提供了工程保障。
