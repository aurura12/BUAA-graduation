\chapter{基于大模型的交通智能体设计}
\section{交通智能体总体架构设计}

本研究的交通智能体采用”慢思考”和”快反应”结合的双层架构。整个架构基于 LangGraph 搭建，核心是一个 ReAct（Reasoning + Acting）推理循环，智能体在这个循环中可以保存和执行多轮推理。

慢思考层由 Qwen3.5-9B 大语言模型来负责。当智能体收到用户的指令后，大模型会先理解用户到底想做什么，然后决定需要调用哪些工具，最后生成结构化的调用指令。这一步是大模型在思考和分析的过程。

快反应层由工具执行引擎来负责。这个引擎收到大模型发出的工具调用指令后，会同时去调用底层的数据查询、深度分析或者流量预测服务，然后把执行结果打包成统一格式返回给大模型。

与传统的线性管线相比，该种双层循环结构具有三个主要的优点。第一，大模型在推理的过程中可以调用很多个工具，大大缩短了系统反应的时间。第二，用提示词模板来约束大模型的行为，防止模型在复杂的交通语境中出现幻觉。第三，工具执行和语义推理在工程上完全解耦，工具链可以独立拓展，不会影响到主要的推理逻辑。

智能体的工作过程分为三部分。第一部分用户提出一个自然语言指令。第二步推理节点（Agent Node）分析指令，按照系统提示词中给出的三个工具来选择调用哪些工具，并生成结构化的工具调用对象。如果大模型原生输出的文本中包含XML格式的工具调用标签，推理节点就会把它们解析成标准的工具调用对象。第三步，工具执行节点（Tool Execution Node）接收到这些工具调用之后，就会对每一个工具调用执行相应的工具函数。推理节点收到执行结果之后，大模型将得到的所有结果综合起来形成一份有条理的分析报告，然后返回给用户。如果推理节点判断不需要调用工具，循环就会直接结束，并输出最终的回答。

\section{语言大模型选择与部署方案}

为了使智能体在交通分析中作出正确的判断，本文使用Qwen3.5-9B做为主要模型。Qwen3.5-9B属于 Qwen3系列,采用 Transformer架构,在预训练阶段使用过大量文本数据进行训练。该模型的参数量比较合适，指令遵循能力强，在理解交通领域的意图以及调度多个工具上表现较好。本研究所用的Qwen3.5-9B为原始精度版本，未做量量化压缩，这样可以保证模型的推理能力不会被削弱。

在部署方式上，本研究将 Qwen3.5-9B 模型部署在本地 GPU 服务器上，通过 vLLM 推理框架对外提供 OpenAI 兼容的 API 服务。vLLM 是一个高性能的大模型推理引擎，它使用 PagedAttention 机制来高效管理 GPU 显存中的键值缓存，从而在保证推理速度的同时支持更大的上下文窗口。以下为具体的部署命令：

\begin{lstlisting}[
    language=bash,
    caption={使用 vLLM 在本地服务器部署 Qwen3.5-9B},
    label={code-vllm-deploy},
    breaklines=true,
    frame=single,
    numbers=left,
]
python -m vllm.entrypoints.openai.api_server \
    --model MODEL_PATH \
    --served-model-name qwen-7b \
    --host 0.0.0.0 \
    --port 8002 \
    --tensor-parallel-size 1 \
    --gpu-memory-utilization 0.45 \
    --max-model-len 20480 \
    --trust-remote-code \
    --api-key "sk-local-api-key"
\end{lstlisting}

部署完成后，智能体通过 HTTP 请求向本地 vLLM 服务端点发送对话消息，调用方式与 OpenAI 官方 API 完全一致。因为模型运行在本地服务器上，数据传输不需要经过外部网络，这既保护了交通数据的隐私性，也避免了云服务可能带来的网络延迟波动。API 的 temperature 参数设置为 1.0，top\_p 设置为 0.95，为模型在生成分析报告时保留了较高的表达灵活性。

在上下文长度方面，vLLM 部署时将最大序列长度设置为 20480 个 Token。这个窗口大小足够让智能体同时感知多个传感器节点在过去较长一段时间内的历史特征数据，并在不截断上下文的前提下进行长时程的语义分析与推理。20K 的上下文窗口为复杂的多工具协同调用和深度交通分析提供了更大的信息容纳空间。

\section{基于状态图的推理逻辑与节点设计}

智能体的核心推理过程被封装在两个相互协作的逻辑节点中，它们通过 LangGraph 的有向状态图进行编排。

\textbf{推理节点（Agent Node）}负责智能体的核心决策。这个节点里有一个系统提示词，规定了智能体能用的三个工具以及每个工具的参数格式。当用户指令进入推理节点后，大模型会先理解用户想做什么，再决定要调用哪些工具，最后输出结构化的工具调用结果。

在工具调用的解析上，推理节点采用双重兼容机制。系统优先使用 LangChain 原生的 \texttt{bind\_tools} 通道，让大模型直接生成符合函数调用规范的结构化数据。如果原生解析未产生工具调用，而模型输出的文本中又包含 \texttt{<tool\_call>} 标签，节点会自动切换到正则回退模式，用正则表达式匹配 \texttt{<function=...>} 和 \texttt{<parameter=...>} 子标签，从中提取工具名和参数值，再构造出等价的工具调用对象。这种双重机制兼顾了标准 API 通道的可靠性和原生 XML 格式的兼容性。

系统提示词是连接用户意图与工具调用的核心桥梁，其设计遵循三个约束原则。第一是工具空间约束，模型的工具选择被严格限定在 simple\_query、deep\_analysis 和 predict\_traffic 三个工具之内，超出范围的调用请求会被直接拒绝，从而防止模型生成无效的工具调用。第二是并行调用规范，提示词鼓励模型在需要时一次性输出多个独立的工具调用标签，以并行方式完成多个子任务，从而提升整体响应效率。第三是数据展示规范，对于预测任务，模型会根据用户指定的时间范围自行截断返回的数据量，并要求以结构化的表格形式呈现结果，避免输出冗余信息干扰后续的分析推理。

\textbf{工具执行节点（Tool Execution Node）}基于 LangGraph 预置的 ToolNode 实现，负责接收推理节点传来的工具调用列表并实际执行。该节点的处理流程分为三个步骤。
第一步就是去重和校验。节点维护已经执行过的调用列表，防止大模型在一轮回复里发出完全相同的工具调用请求。每一个调用都会检查它的工具名是否在可用的工具映射表里。

第二步并行执行。所有的合法工具调用都会被并发地发送到相应的工具函数里去执行。三个工具分别封装了底层FastAPI数据服务的HTTP请求，可以有效地减少多工具协同调用时的响应时间。

第三步为结果汇总。各个工具的执行结果用统一的消息格式传送给推理节点，供大模型做下一步的综合分析。如果某一个调用在执行过程中出现异常，那么节点就会产生相应的错误信息来保证系统不会因为单个工具的故障而中断整个推理过程。

\textbf{条件路由机制}来决定下一步应该执行什么样的操作。LangGraph状态图只有一条条件边，它的作用就是检查推理节点输出的消息中是否有tool\_calls属性。如果该属性不为空，说明大模型需要调用工具，系统就将请求转发到工具执行节点。工具执行完毕后将结果返回到推理节点，由推理节点继续判断。若为空，则大模型已经完成全部分析，系统就停止工作，把最后的结果告诉用户。

这种”推理-执行-再推理”的循环方式比传统的线性流程更灵活，也能更好地处理各种异常情况。用户发出一个请求后，智能体可以根据实际需要调用多次工具，一步一步地把交通数据分析得更深入。

\section{执行层工具链设计与实现}

项目的执行层把各个核心工具封装成基于 FastAPI 异步框架的微服务，让智能体能够实时访问底层数据。整个执行层通过 Uvicorn 服务器进行部署，把存在 SQLite 数据库中的 PeMS08 交通数据变成可以随时调用的计算服务。

基础流量感知工具通过 \texttt{/flow/point} 接口来接收智能体的请求。智能体会发送实体标志和时间参数（ISO-8601格式），后端用SQL语句从dyna动态表里查找到相应的数据。为了使数据提取更加准确、稳定，底层数据库连接采用的是sqlite3.Row工厂模式。因此交通流量、道路占有率、平均速度等数值都可以用结构化键值对的形式返回给智能体。这样写可以防止各个模块之间传递数据时出现格式不一致的情况。

深度分析工具用来满足更复杂的分析需求。它通过 \texttt{/flow/history} 接口来查询历史流量数据。服务端根据智能体发送的查询时间范围参数，使用 Python 的 datetime 类来自动计算出起止时间，然后从数据库中提取连续的流量记录。为了让智能体处理长序列数据时更加高效，该工具在返回结果之前先做了一次初步的特征聚合，只保留流量变化明显的那些时间节点。这样智能体就能基于这些数据来判断当前路段的拥堵风险。

预测计算工具负责把智能体和底层的 PDFormer 时空模型连接起来。它不只是查询单个传感器的数据，而是会收集全部 170 个传感器在过去 12 个时间步的历史数据，组成完整的时序特征向量。基于 FastAPI 的微服务设计让感知和计算两个环节互相独立。智能体只需要发送一个 JSON 格式的请求，预测引擎就会自动运行。预测结果会按照统一格式返回给智能体，方便后续展示。此外，系统还集成了一个基于文件的日志记录模块，每次 API 调用都会被记录下来，为系统稳定运行提供了保障。
