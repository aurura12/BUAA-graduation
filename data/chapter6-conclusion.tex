\chapter{总结与展望}

本章对全文工作进行全面总结，梳理本文在交通智能体系统设计与实现方面的四个主要贡献——双层驱动架构、本地化模型部署与工具链集成、智能体测试方案、以及实验中发现的数字歧义问题。同时分析当前研究在数据集覆盖范围、工具链广度和硬件资源方面存在的不足，并展望未来在实时数据接入、多模态感知、大模型升级和工具链扩展等方向的发展可能。

\section{本文工作总结}

本文针对城市交通管理中自然语言交互与时空数据智能分析的实际需求，设计并实现了一个基于大语言模型的交通智能体系统。围绕研究目标中提出的系统架构设计、慢思考与快反应机制、交通预测模型集成、数据访问模块以及系统原型验证五个方面，逐一完成了从架构设计到代码实现再到实验验证的完整工作。本文的主要工作总结如下。

第一，设计了一种面向交通领域的智能体双层驱动架构。该架构由慢思考层和快反应层组成，对应研究目标中提出的“慢思考”与“快反应”分离设计思路。慢思考层由 Qwen3.5-9B 大模型负责理解用户意图、选择工具并生成调用指令，能够把模糊的自然语言需求拆解成具体的子任务序列，通过 ReAct 循环进行多步推理。快反应层由工具执行节点负责并行调用底层数据服务，包括实时态势查询、历史趋势分析和未来流量预测三个核心工具，对简单请求直接返回结果，绕过大模型的推理过程以减少响应延迟。两层之间通过 LangGraph 的 ReAct 推理循环进行编排，由条件路由边根据模型输出中是否包含工具调用指令来自动切换推理节点和工具执行节点，实现了推理与执行的有效分离。在工具调用的解析上，系统采用了 LangChain 原生 bind\_tools 优先、正则表达式回退的双重兼容机制，兼顾了标准 API 通道的可靠性和原生 XML 格式的灵活性。

第二，完成了大模型的本地化部署与工具链集成，并集成了交通预测模块与数据访问模块。在预测模型方面，系统集成了 BIGCity 时空预测模型作为核心预测工具，该模型基于 Transformer 架构，通过地理、语义和时间三种注意力机制建模交通数据的时空依赖关系，在 PeMS08 数据集上进行了训练和验证。在模型部署方面，将 Qwen3.5-9B 原始精度模型通过 vLLM 推理框架部署在本地 GPU 服务器上，支持 20K Token 的上下文窗口，并通过 PagedAttention 管理和前缀缓存等技术优化了显存利用和推理效率。在数据访问方面，围绕 PeMS08 交通数据集，按照 ST 原子文件的格式将多源异构数据统一为标准化的 .geo、.rel 和 .dyna 文件，并导入 SQLite 数据库通过 FastAPI 提供 REST 接口。三个工具通过 FastAPI 微服务架构封装，与智能体决策层之间通过标准 HTTP 协议进行解耦通信，每个服务可以独立部署和扩展。

第三，设计并执行了一套覆盖七类场景的智能体测试方案，完成了系统原型的实验验证。在预测模型评估方面，将 BIGCity 与 HA、ARIMA、SVR、STGCN、DCRNN、GWNET 六个基线模型在 PeMS08 数据集上进行了对比，BIGCity 在 MAE、MAPE、RMSE 三项指标上均取得了最优结果。在智能体验证方面，基于 37 条测试用例，从意图识别、工具调度、报告质量和异常处理四个维度对智能体进行了系统性评估。实验结果表明，智能体在所有 37 条测试用例中均正确识别了用户意图，能够适应五种不同的自然语言时间格式，在传感器查询、拥堵研判、流量预测和多工具协同等场景下均能生成结构化的专业分析报告。在异常处理方面，智能体对传感器不存在、时间超范围和历史数据不足等异常情况均做出了有意义的降级处理，未出现崩溃或幻觉。


\section{研究不足}

尽管本系统在设计理念和实验验证上取得了一定的成果，但在数据、功能和硬件三个方面仍然存在明显的不足，制约了系统在更大规模真实场景中的应用。

数据集方面的限制。实验使用的 PeMS08 数据集仅覆盖 2016 年 7 至 8 月的历史数据，时间跨度只有两个月，且不支持实时数据接入。这两个因素共同导致了两个问题。一是智能体对相对时间查询（如“昨天”）的响应受限——虽然时间格式解析本身正确，但数据集时间范围内不存在对应的日期数据，查询只能返回空结果。二是无法支持实时交通状况查询，用户问“当前拥堵情况怎么样”时，系统只能给出数据集对应时间段的历史数据，而不是实时的路况信息。此外，数据来源仅限于高速公路传感器网络，未覆盖城市道路、交叉口、公共交通等多样的交通场景，也缺少交通事故、天气状况、大型活动等外部事件数据。这意味着模型学到的交通模式局限于高速公路的日周期变化规律，在更复杂的城市路网场景下效果如何还有待验证。

工具链覆盖面的不足。当前系统实现了态势查询、深度分析和流量预测三个核心工具，功能覆盖主要集中在数据查询和数值预测两个环节，尚未覆盖更丰富的交通管理功能。比如路径规划工具可以让智能体回答出行路线推荐类问题，拥堵溯源工具可以从多维度分析拥堵的根因（事故、施工还是上游车流过载），交通信号灯优化工具可以根据实时流量数据生成信号灯调整建议。工具链的广度直接决定了智能体能够处理的业务范围，目前的覆盖范围还有较大的扩展空间。此外，当前三个工具都只支持单一传感器粒度的查询，不支持区域级的数据聚合和对比分析，比如查询“整个海淀区的平均车速”或“对比早高峰和晚高峰的拥堵路段数量”这类需要跨节点汇总的任务还无法直接完成。

硬件资源的约束。受限于单张 RTX 4090 的 24 GB 显存，Qwen3.5-9B 是当前单卡条件下能部署的最好模型，更大体量的模型（如 70B 级别）虽然具有更强的推理和多步规划能力，但由于显存限制无法在现有硬件上运行。这在一定程度上限制了系统在极端复杂交通场景下的推理上限——比如需要同时分析多个路段的拥堵传播趋势、评估绕行方案的效果、并结合历史相似事件给出处置建议这类多因素综合推理任务，9B 模型的推理深度和准确性还有提升空间。此外，vLLM 部署时 gpu-memory-utilization 设为 0.5，预留了显卡的一半显存用于其他服务，在并发请求较多时可能会因显存不足而导致请求排队或超时。如果后续需要支持多用户同时访问，当前的单卡部署方案在并发能力上也是一个瓶颈。

\section{未来展望}

针对上述不足，未来的工作可以从系统架构、感知能力、模型能力和工具链四个方向展开，逐步将系统从一个原型验证系统发展为可实际部署的智能交通辅助决策平台。

在系统架构方面，可以逐步接入实时交通数据流，将系统从基于历史数据的离线分析升级为真正的在线交通感知与决策系统。接入实时数据后，智能体的“昨天”查询将能够返回真实的昨日数据，“当前路况怎么样”将不再是一个需要推测的问题。实时数据流还可以支持智能体进行持续监测和自动告警——当某个路段的流量或速度超过预设阈值时，系统可以主动向交通管理者推送预警信息。

在多模态感知方面，可以将视觉大模型（如 GPT-4o、LLaVA 等）接入系统 \upcite{ref32_GCTX202406013}。目前的智能体只能处理文本和数值数据，但交通管理者在实际工作中经常需要查看监控画面来判断事故类型和拥堵程度。接入视觉模型后，智能体可以直接“看懂”交通监控画面——判断一辆停着的车是因为交通拥堵还是因为发生了事故，识别路面积水或散落物等异常情况，甚至可以通过分析视频流中的车辆密度来辅助验证预测模型的结果。视觉信息和数值信息的结合将为交通态势感知提供一个更加完整的视角 \upcite{ref22_radford2021learning, ref27_JSJYGG202118006}。

在大模型升级方面，随着硬件条件改善，可以部署推理能力更强的大模型（如 DeepSeek-R1、GPT o1 系列等）\upcite{ref39_zhang2025application}。当前使用 Qwen3.5-9B 在大多数场景下表现良好，但在多步规划和复杂逻辑推理方面仍有提升空间。推理模型通过强化学习学会了在给出答案之前进行长时间的自我推理，这种能力对于需要综合多因素判断的交通分析任务会有很大帮助——比如评估一个路口的新信号配时方案在多大程度上能缓解拥堵，这个问题需要考虑历史流量模式、周边路网的承载能力和时间段的特殊性，正是推理模型擅长处理的场景。

在工具链扩展方面，可以引入更多交通领域的专用工具。路径规划工具可以让智能体回答“从A点到B点走哪条路最省时”这类问题。拥堵溯源工具可以分析当前拥堵的根因——是因为事故、施工还是因为上游车流过大。信号配时优化工具可以让智能体根据实时流量数据自动生成信号灯配时调整建议。工具链越丰富，智能体能够处理的交通管理场景就越多。

在多智能体协同方面，可以将单智能体架构扩展为多智能体系统。不同的智能体可以承担不同的角色——一个智能体负责实时交通监控和告警，另一个负责长期交通规划和策略分析，第三个负责公众出行信息服务。它们之间通过消息传递进行协同，比单智能体处理复杂任务时有更高的效率和更好的容错性。这种多智能体架构是未来交通智能体系统的一个重要发展方向。
